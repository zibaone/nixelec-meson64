# H.264 10 bits (Hi10P) : pourquoi le VPU ne le prend pas, et ce qu'il faudrait

État au 2026-10-30, N5 (S905L, noyau 7.0.14, `meson-amvdec`).

## Constat mesuré

```
v4l2-ctl -d /dev/video0 --list-formats-out
  [0]: 'S264'  (H.264 Parsed Slice Data, compressed)
  [1]: 'S265'  (HEVC Parsed Slice Data, compressed)
  [2]: 'MG2S'  (MPEG-2 Parsed Slice Data, compressed)
  [3]: 'VP9F'  (VP9 Frame, compressed)

v4l2-ctl -d /dev/video0 --list-formats      # capture
  [0]: 'NM12'  (Y/UV 4:2:0 (N-C))           # NV12M, 2 plans
```

Un H.264 10 bits (profil High 10) n'a **aucun** format de sortie correspondant :
`S264` décrit des tranches 8 bits. Le banc le confirme — notre hwaccel refuse
(`Failed setup for format drm_prime`) et le décodage retombe en logiciel, où il
fonctionne (19 s de CPU pour 10 s de 1080p30, soit ~2 cœurs).

À comparer avec HEVC : `S265` **plus** `.max_bit_depth = 10` font que le HEVC
10 bits décode en matériel (mesuré : 0,41 s de CPU pour 10 s).

## Où c'est dans le code

Tout est dans le pilote, `patches/kernel/meson64-vdec-7.0/` :

- `amlogic-0121-…-H.264-decoding.patch` — chaque entrée de format porte
  `.max_bit_depth = 8` (lignes 201, 226, 251, 276, 302, 328) et la capture
  n'annonce que `V4L2_PIX_FMT_NV12M` (ligne 209 et suivantes).
- Le même fichier refuse explicitement la profondeur > 8 à l'analyse du SPS
  (~ligne 3161) :

  ```c
  if (sps->chroma_format_idc != 1 || sps->bit_depth_luma_minus8 || …)
  ```

- `amlogic-0122-…-HEVC-decoding.patch` — les mêmes entrées portent
  `.max_bit_depth = 10`, et le cœur compare la profondeur réelle du flux à ce
  maximum (`sps->bit_depth_luma_minus8 + 8 > fmt->max_bit_depth`).

Le refus n'est donc pas un oubli de configuration : le pilote H.264 n'a **aucun**
chemin de registres pour une profondeur supérieure à 8, ni format de capture
10 bits associé.

## Ce qu'il faudrait corriger, dans l'ordre

1. **Pilote noyau** — le vrai travail :
   - ajouter une entrée de format (`.max_bit_depth = 10`) ou un second fourcc
     (`S2 10` / `S264_10BIT`) dans les `pixfmts_out` du décodeur H.264 ;
   - élargir `pixfmts_cap` à un format 10 bits (`P010` / `NV12_10`) ;
   - écrire la configuration VPU correspondante : les registres Amlogic
     (`AV_SCRATCH_*`, `AV_MB_COUNT`…) supposent aujourd'hui un bitstream 8 bits ;
     c'est là que se trouve l'inconnue, pas dans le V4L2 ;
   - relâcher le test SPS ci-dessus.
2. **FFmpeg (`nix-v4l2-request`)** — le hwaccel `v4l2_request_h264.c` déclare une
   seule configuration, `AV_PIX_FMT_DRM_PRIME` 8 bits ; il faudrait une variante
   10 bits (P010 → `DRM_FORMAT_P010`) et le passage des paramètres de tranche
   Hi10P (S264 ne transporte pas les offsets de bit-depth).
3. **Kodi** — rien à faire : `CDVDVideoCodecDRMPRIME` accepte déjà P010 ; c'est la
   seule couche qui est prête.

## Faut-il le faire ?

Non, en l'état, pour trois raisons mesurables :

- **Aucune preuve que le silicium sache le faire.** Le VPU GXL est documenté par
  Amlogic pour du H.264 8 bits et du HEVC 10 bits — exactement ce que le pilote
  expose. Rien dans le code amont ne suggère un mode Hi10P caché.
- **Le repli logiciel fonctionne** : 19 s de CPU pour 10 s de vidéo (2 cœurs sur
  les 4), image et son corrects. Un flux Hi10P reste regardable, au prix du CPU.
- **Le Hi10P est rare** : les diffusions IPTV et les services de streaming
  utilisent du H.264 8 bits ou du HEVC. Le cas se rencontre surtout dans des
  encodages anime historiques.

Si la question revient, le test qui trancherait coûte peu : écrire un
`v4l2-ctl --try-fmt-video-out` avec un fourcc 10 bits sur un pilote modifié et
voir si le matériel produit des images — mais tant qu'aucune source ne documente
le mode, c'est du travail à l'aveugle dans une séquence de registres non
documentée.

## Vérifier l'état actuel d'une carte

```bash
v4l2-ctl -d /dev/video0 --list-formats-out   # S264 seul = pas de 10 bits
ffmpeg -hwaccel drm -hwaccel_output_format drm_prime \
       -c:v h264 -i hi10p.mp4 -f null -      # « Failed setup » = repli logiciel
```

# N5 — sortie HDMI muette au premier boot Kodi, relevé du 2026-10-28

> Image `magicsee-n5-kodi` (noyau 7.0.14, patchs `meson64-vdec-7.0`), premier
> démarrage du profil kiosque. **Résolu : le câble HDMI était défectueux.**
> Le téléviseur ne recevait ni les 5 V ni le signal : aucune détection, ce qui
> se lit exactement comme une sortie morte côté logiciel. Deux vrais défauts ont
> été trouvés en chemin (ci-dessous), mais aucun n'était la cause.

## État final, mesuré

Après remplacement du câble, sans changer une ligne de code :

| interrogation | avant | après |
|---|---|---|
| `card0-HDMI-A-1/status` | `disconnected` | `connected` |
| `card0-HDMI-A-1/edid \| wc -c` | **0** | **256** |
| `modes` | vide | 4K, 1440p, 1080p (tous rates), 720p, 576p… |
| Kodi | aucune surface | `GUI format 1920x1080, Display 1920x1080 @ 60` |
| rendu | — | `GL_RENDERER = Mali450`, `using the gbm windowing system` |

Le téléviseur annonce du 4K ; Kodi tourne en 1080p60, comme prévu par le
`video=HDMI-A-1:1920x1080@60D` de `modules/system/kodi.nix` (GXL ne compose pas
une interface 4K de façon fluide).

## Le piège de lecture, à retenir

Tant que le câble était mauvais, `status` affichait `connected` — **parce que le
mode était forcé** (`D` = `DRM_FORCE_ON_DIGITAL`), pas parce que le téléviseur
était vu. Un `status=connected` obtenu sous forçage ne prouve rien :

- la preuve de détection est **`edid > 0`** ;
- un connecteur forcé masque aussi le hotplug, donc une panne de câble future.

Corollaire de méthode : **tester le câble avant toute archéologie noyau**. Un
câble mort produit exactement la même signature qu'un PHY éteint —
`disconnected`, `edid=0`, aucun HPD, aucun message EDID dans `dmesg`.

## Ce qui a été réfuté en chemin

- **Un mauvais DTB** : les DTB GXL du noyau 7.3 (`p212`, `p281`, `tx3-mini`,
  `libretech-cc`, `nexbox-a95x`) déclarent tous `regulator-hdmi-5v` sur la même
  ligne 19 du contrôleur periphs et `hdmi-supply` sur `hdmi-tx`. Changer de carte
  n'aurait rien déplacé.
- **Un interrupteur 5 V piloté en GPIO** : `HDMI_5V` se déclare `enabled`
  (3 utilisateurs) alors que `gpio-19` reste `out lo`. Après le changement de
  câble, **le GPIO est toujours bas et tout fonctionne** : ce pin n'est pas
  l'interrupteur d'alimentation de cette carte, et l'incohérence
  `enabled`/`out lo` n'était pas le défaut.
- **Un HPD non câblé** : HPD fonctionne dès que le câble est bon.

## Deux vrais défauts trouvés au passage

### 1. Le `video=` n'arrivait pas au noyau

`/proc/cmdline` sur la cible ne contenait pas le `video=` posé par
`modules/system/kodi.nix`. Cause : `modules/boards/magicsee-n5.nix` déclare

```nix
boot.kernelParams = lib.mkForce [ "console=ttyAML0,115200n8" "cma=256M" ];
```

et sur une option de type liste, `mkForce` (priorité 50) **jette sans un mot**
toute définition de priorité normale. Aucune erreur, aucune alerte à l'éval.

Le piège symétrique a été vérifié : passer le module de carte en `mkDefault` ne
compose pas non plus — la définition de `nixbian/nix/parts/nixos-module.nix`
(`root=LABEL=nixos`, `console=ttyS0,115200`, priorité 100) gagne **en entier**,
et la carte perd `console=ttyAML0` et `cma=256M`, donc sa console série et la
mémoire du VPU.

Composition correcte : `mkForce` **des deux côtés**, même priorité, les listes se
concatènent. Vérifié avant build, puis dans les fichiers de boot de l'image :

```bash
nix-store -q --outputs \
  "$(nix-store -q --references "$(nix-store -qd /nix/store/<image>.img)" \
     | grep n5-boot-files)" \
| xargs grep -rhoE '(video|console|cma)=[^ "\\]*' | sort -u
# → cma=256M / console=ttyAML0,115200n8 / video=HDMI-A-1:1920x1080@60D
```

Lire l'option (`nix eval …config.boot.kernelParams`) ne suffit pas : c'est le
script de boot gravé dans l'image qui fait foi. Règle générale : skill
`nix-derivation-verification`.

### 2. Ne pas délier/relier `meson-dw-hdmi` à chaud

Testé pour forcer une ré-initialisation du PHY : `unbind` laisse un trace noyau,
`bind` échoue en `-16` (EBUSY), le sous-système DRM ne revient pas, et l'arrêt
suivant part en `Kernel panic - not syncing: Attempted to kill init!
exitcode=0x0000000b` (PID 1 segfault). La carte exige alors une coupure
d'alimentation : un reboot propre est le seul moyen de réinitialiser la chaîne.

## Méthode — piloter la cible par l'UART

La console série (`ttyAML0`, 115200 8N1, `/dev/ttyUSB1` côté hôte) donne un shell
root, ce qui permet d'interroger `/sys` sans reconstruire d'image :

```bash
python3 /tmp/opencode/uart-cmd.py 'cat /sys/class/drm/card0-HDMI-A-1/status'
```

Le script ouvre le port, envoie la commande, lit la réponse ; il gère le
`login:` en répondant `root`. **Ne pas lancer deux lecteurs sur le même port** :
le logger de boot et le script se volent les octets — arrêter le logger d'abord
(`pkill -f "uart-log[.]py"` ; sans les crochets, le motif correspond à la ligne
de commande du shell qui l'exécute et le tue lui-même).

## Accès réseau de qualification

L'image kiosque n'a ni Nix ni `sshd`. `modules/system/lab-ssh.nix` (non
versionné) ouvre `openssh` root par mot de passe (`n5lab`) et fixe
`192.168.77.2/24` sur `end0`, en face de l'hôte en `192.168.77.1/24`. À retirer
de toute image exposée.

Le lien direct n'a **pas de serveur DHCP** et l'ARP met une bonne minute à se
peupler après un boot : un `ping` immédiat échoue alors que la carte est déjà en
ligne. Vérifier `ip neigh` avant de conclure à une panne réseau.

## Le défaut trouvé : l'image kiosque n'embarquait pas les microcodes

Symptôme, avant correctif — le décodeur était bien *choisi*, mais chaque paquet
échouait :

```
CDVDVideoCodecDRMPRIME::Open - using decoder H.264 / AVC / MPEG-4 AVC
CDVDVideoCodecDRMPRIME::AddData - send packet failed: Invalid data found (-1094995529)
CDVDVideoCodecDRMPRIME::GetPicture - receive frame failed: Invalid data found
```

`ffmpeg` traduit l'absence de microcode en `AVERROR_INVALIDDATA`, ce qui fait
soupçonner le flux. Seul `dmesg` nomme la cause :

```
meson-amvdec c8820000.video-codec: Direct firmware load for
    meson/vdec/gxl_h264_multi.bin failed with error -2
```

Sur la cible : `/run/current-system/firmware/` contenait `ath10k` et `qca`
(WiFi) mais **pas** `meson/vdec/`. Cause : `modules/system/minimal.nix` câble
`nixelec.extraFirmware`, mais seule la configuration de qualification le
renseignait — `decode-tools.nix` posait `nixelec.extraFirmware` directement, et
la configuration kiosque n'en posait rien.

Correctif : `modules/system/vdec-firmware.nix` porte la dérivation (LibreELEC
`meson-firmware`, épinglé `662b843`) et l'option `nixelec.vdecFirmware.enable`,
activée par défaut dans `modules/system/kodi.nix`. `decode-tools.nix` importe ce
module au lieu de dupliquer la dérivation :

```bash
nix eval .#nixosConfigurations.<cfg>.config.nixelec.extraFirmware \
  --apply 'l: map (p: p.drvPath) l'
# magicsee-n5-kodi   → vs76qin4…-meson-vdec-firmware.drv
# magicsee-n5-decode → vs76qin4…-meson-vdec-firmware.drv   (même dérivation)
```

Après flash : 13 microcodes dans `/run/current-system/firmware/meson/vdec/`.

## Le `video=` : une préférence, pas un forçage

`video=HDMI-A-1:1920x1080@60` est conservé **sans suffixe `D`**. Avec `D`
(`DRM_FORCE_ON_DIGITAL`) le connecteur se déclare toujours `connected`, le
hotplug est désactivé, et une panne de câble devient indiscernable d'un PHY
mort — c'est exactement ce qui a coûté une session de diagnostic
(`n5-hdmi-2026-10-28.md`).

Le paramètre doit être posé en `lib.mkForce` : le module de carte force lui
aussi `boot.kernelParams`, et à priorité inégale la liste du forçage jette la
nôtre en silence. À priorité égale, les listes se concatènent.

Kodi choisit malgré tout 1080p60 (`GUI format 1920x1080`) : pas besoin de brider
sa résolution dans `guisettings.xml`.

## Méthode de mesure

Lire un fichier sans toucher au service : un drop-in systemd dans
`/run/systemd/system/kodi.service.d/` remplace `ExecStart` par
`kodi <fichier>`, puis `daemon-reload` + `restart`. Le retrait du drop-in rend
le service à son état normal — rien n'est persisté.

Trois pièges rencontrés :

1. **`systemctl show -p MainPID` renvoie le wrapper shell**, pas `kodi.bin`
   (`…/bin/.kodi-wrapped` lance `…/lib/kodi/kodi.bin`). Mesurer le CPU sur ce
   PID donne `0,00 s` en permanence. La valeur fiable est la comptabilité
   cgroup : `systemctl show -p CPUUsageNSec kodi`.
2. **Un log créé par root est illisible pour l'utilisateur `kodi`** : `-l
   /tmp/x.log` précédé d'un `: > /tmp/x.log` en root produit un fichier vide,
   et on conclut à tort que Kodi n'écrit rien. Lire son log habituel,
   `/var/lib/kodi/.kodi/temp/kodi.log`.
3. **L'échantillon doit être celui qui a été validé sur le VPU.** Le flux
   rejeté au premier essai n'était pas en cause (le microcode manquait), mais
   garder la recette connue évite de confondre deux causes :
   `testsrc2` 1920x1080@30, `-c:v libx264 -profile:v high -level 4.1 -b:v 4M
   -g 60 -threads 1 -x264-params keyint=60:min-keyint=60:scenecut=0`
   (`modules/system/decode-tools.nix`).

## Deuxième mesure — 2026-10-31, flux d'addon sous HavenOS

Contexte : HavenOS kiosque installé sur la **eMMC** (système
`glxnsrfm…`, noyau 7.0.14), lecture d'un flux **1920x1080 H.264** servi par
`inputstream.adaptive` depuis un addon — donc un chemin différent du fichier
local du 28/10 (réseau, conteneur, débit adaptatif).

| point | valeur mesurée |
|---|---|
| décodeur retenu | `CDVDVideoCodecDRMPRIME::Open - using decoder H.264 / AVC` |
| descripteurs tenus par `kodi.bin` | `/dev/video0`, `/dev/media0`, `/dev/dri` |
| interruptions `vdec` (`/proc/interrupts`, IRQ 44) | **2 101** pendant la lecture |
| repli logiciel | aucun `CDVDVideoCodecFFmpeg::Open` |
| erreurs | aucun `send packet failed`, aucun `receive frame failed`, aucune image jetée |
| CPU par fil | 30,4 % et 20,1 % (fils principaux), 12,0 / 8,8 / 4,9 % (`VideoPlayer`), **4,0 % (`av:h264`)** |
| CPU total | `kodi.bin` ≈ 95 % d'un cœur, système à 48 % au repos |

Le fil `av:h264` à 4 % est le point intéressant : dans le chemin stateless,
FFmpeg **analyse** les NAL et les pousse vers le périphérique V4L2 ; il ne
décode pas. Un décodage logiciel de 1080p saturerait ce fil à 100 % et plus.
Le coût restant est le rendu OpenGL via `lima` (30 % + 20 % sur les fils
principaux), pas le VPU.

Niveau de preuve : **P2** (pipeline fonctionnel sur une seule machine) et, pour
l'installation elle-même, **P5** — le boîtier a redémarré sans carte SD et
retrouve son kiosque.
